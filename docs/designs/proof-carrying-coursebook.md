## Problem Statement

Turn a YouTube playlist into a coherent, readable eBook (PDF + source) with an
LLM pipeline. Two hard rules: no hallucinations, and a pipeline someone else can
run to regenerate the book. "No hallucinations" is made into a guarantee we can
measure: every factual sentence is cited and judged against its source; anything
unsupported is rewritten, removed or reviewed by a person; and a blinded audit
publishes the remaining error rate, which the release gate holds below a
threshold. The book's front matter states this guarantee and its measured rate,
rather than promising zero. First target: "Building LLMs from scratch" (Dr Raj
Dandekar; 43 lectures, 31.0 h, 12-94 min each). The engine must work for other
playlists too; it must not be fitted to this one.

Goal: an evaluation assignment meant to impress. Deadline: 2+ weeks.

Starting point (measured 2026-10-11): playlist list saved and hashed (43
entries), captions for 1/43 lectures, 0 chapters, model never called, reportlab
PDF that handles plain prose only, 9 synthetic tests passing, no git commits.

## What Makes This Cool

A **proof-carrying textbook**: the book shows the evidence behind its own claims.
- Every paragraph links to the caption lines that support it, at the exact second
  (popovers in the HTML edition, a compact source key in the PDF margin; see
  Citation contract).
- The book's code runs in CI. Claims that can be computed (parameter counts,
  tensor shapes) are test assertions.
- The hallucination check is measured: false claims are planted in drafts and
  the report states how many the verifier caught, plus a support rate per chapter.
- Whiteboard moments become clean diagrams. Each diagram is turned back into
  plain claims and checked against the source.

## Constraints

- Assignment: a book, not video summaries; grounded claims; a pipeline others can rerun.
- User: "we also wanna make sure that we are not overengineering for this
  specific playlist, it should be reproducible for other playlist".
- YouTube blocks transcript requests from cloud IPs, so CI cannot capture live.
- Model output varies between runs, so a fresh run is never byte-identical.
- Reuse rights for the source videos are unknown. The reference repo
  `rasbt/LLMs-from-scratch` is Apache-2.0.
- Not installed on this machine yet: Quarto, Pandoc, Typst (ffmpeg is present).
- One person (Mahima) does all human review; no second reviewer is assumed.

## Premises (all agreed)

1. **Concept chapters.** The model proposes the outline across all lectures; a
   person approves the outline once. Not one chapter per video.
2. **Checking claims (revised after the second opinion).** The checker runs on
   every paragraph. A person signs off the outline plus every paragraph that is
   flagged or low-confidence. A blinded audit of 100 auto-passed claims is
   published, and release is blocked if its error rate exceeds a set threshold.
3. **Snapshot replay.** Hashed captions and cached model responses are committed,
   so `make book` rebuilds offline. A fresh run is a separate, documented mode.
4. **Config, not code.** Topic, reader profile, reference pack and code language
   live in a config file for each playlist. CI also builds a second, small,
   different playlist.
5. **Optional stages.** The code, figures and reference-pack checks are switched
   on or off in config; when off, they leave no section in the book and the report
   lists them as "skipped (disabled)". "External check" means the configured
   reference pack only. A general web-search stage is out of scope.

Reference policy: the lectures are the source of the teaching. A configured
"reference pack" (here `rasbt/LLMs-from-scratch`, pinned to a commit, with
credit) supplies code listings and acts as a second check on the facts. A
disagreement between the two is flagged, never silently resolved.

## Recommended Approach: B, built slice-first

### Pipeline (every stage writes a hashed artifact; `[]` = optional stage)

```
config/<playlist>.json
   |
1 capture ----> manifest + raw captions (content-addressed; fallback: yt-dlp subs / local Whisper)
2 segment ----> ~30 s windows `VIDEO@S-E`; each line kept as `[S] text`, ID `VIDEO@S`
                (compact: removes the ~9x JSON overhead, keeps line IDs)
3 extract ----> teaching points per 15-min chunk: {id, kind, text, line_ids, importance 1-3}
                + per-lecture inventory (points per 15 min; zero-point spans flagged)
                kind = definition | claim | procedure | code | equation | analogy | visual_ref
4 outline ----> per-lecture-group outlines, then merged into a book outline (stays inside
                the context window); coverage: every importance-3 point placed or dropped
                with a reason; code points mapped to reference files
                ==> HUMAN APPROVES outline + code mapping (hash recorded)
5 write ------> Markdown per section; sentence-level citation IDs (see Citation contract)
6 verify -----> atomic claims -> judge (supported / partial / unsupported + confidence)
                against the cited lines + their windows (+ reference pack); one rewrite pass, re-judged; still
                partial/unsupported or confidence < 0.7 -> review queue
                planted-false-claim test -> catch rate; review queue = flagged + low-confidence
                ==> HUMAN reviews queue; blinded audit of 100 auto-passed claims
[7 code] -----> reference-pack files mapped to sections; listings run in CI; computable
                numeric claims become pytest assertions
[8 figures] --> visual_ref points -> frames (ffmpeg; hash recorded) -> vision model ->
                SVG/Mermaid -> diagram claims judged against caption lines within +/-60 s;
                fail -> figure dropped, prose kept, counted in report
9 render -----> Quarto book: HTML (citation popovers, video links) + PDF; evaluation report
```

### What carries over from the current code
- `core.snapshot`, `digest`, the manifest and the playlist-order tests
  (unchanged).
- `review_is_current` (the review hash check), reused for the flagged-paragraph
  review files.
- `validate_chapter`'s citation-ID check, kept as the cheap first gate before the
  claim judge.
- `build.py`'s reportlab renderer is **replaced** by a Quarto project generator.
- Chapter-per-video drafting in `model.py` is **replaced** by stages 3-5.

### Reproducibility contract
- Every model call is cached under `data/<playlist>/cache/<sha256>.json`, keyed
  by prompt template hash, inputs hash, model ID and parameters.
- `make book` replays from the cache with no network access. `make fresh`
  makes live calls and records new cache entries.
- CI: unit tests, offline replay of both playlists, code tests, and a
  comparison of output hashes for the Markdown/HTML.


### Contracts (resolved from spec review round 1)

**Citation contract (R1-4, R1-5, R1-6).**
- Evidence unit: the original caption line, ID `VIDEO@S` where S is whole
  seconds from the start (shown as h:mm:ss; works past 60 minutes). The 30 s
  windows are only groupings sent to the model; citations always point to lines.
- Sentence types: *factual* sentences must cite at least one caption line;
  *technical* sentences may also cite the reference pack (`ref:<path>#L<a>-<b>`);
  *connective* sentences (transitions, signposting) need no citation, but the
  judge checks that they contain no factual claim. `validate_chapter` enforces this.
- Rendering: sentence IDs stay in the data. Readers see one source marker per
  paragraph: in the HTML, a hover shows the quoted lines with video links; in the
  PDF, a margin key such as "L08 12:30, 14:05". Each chapter ends with a source
  list. No per-sentence footnotes, so no footnote-label collisions.

**Planted-claim test (R1-7).** For each chapter, a script asks the model for 20
false variants of verified claims: changed number, swapped term, reversed cause,
unsupported addition, wrong attribution (4 each), about 200 across the book.
They are inserted into a copy of the chapter in `eval/plant/`. The judge runs
without knowing which claims are planted. Catch rate is reported by type. Release
is built only from the main chapter tree, and a test checks that no planted ID
or text appears in any output.

**Blinded audit (R1-8).** The auditor is Mahima (or a peer if one is available).
The sample is 100 auto-passed claims, spread across chapters and claim kinds,
mixed with 20 planted claims to measure how attentive the auditor was. The
auditor sees each claim and its cited lines, never the judge's verdict. A
*material error* is a claim that contradicts its source, or is unsupported by it,
in a way that would mislead a learner. Release is blocked when the observed rate
exceeds 2% (more than 2 errors in 100). A sample smaller than 50 claims must have
zero material errors. Then:
fix those claims, adjust the judge prompt, re-verify the affected chapters, and
audit a fresh sample.

**Edits and re-checking (R1-9).** Every rewritten or human-edited paragraph goes
back through claim extraction and judging. Its review record is tied to the
post-edit hash through `review_is_current`.

**Lecture vs reference disagreements (R1-10, R1-16).** In the outline stage, the
model proposes which reference-pack files match which code teaching points, and
the person approving the outline approves this mapping too. Any difference
between the lecture and the reference (in a claim or in code) goes to the review
queue with three outcomes: follow the lecture, follow the reference, or show
both with a short note to the reader. An unresolved disagreement blocks release.

**Approvals and builds (R1-12).** Approval and review records are committed under
`data/<playlist>/approvals/`, each tied to a content hash. `make book` always
builds; if any approval is missing or out of date, the output carries a DRAFT
watermark and the report lists why. `make release` fails in that case, and so
does the CI release job.

**Source rights: two replay modes (R1-1, R1-2).**
- *Public data:* captions are committed. CI replays every stage offline,
  including the hash check that ties each caption line to its citations.
- *Private data:* only hashes and cached model outputs are committed. CI replays
  writing, judging and rendering from the cache, and checks the hash chain.
  Checking that the evidence matches the raw captions runs locally against the
  private data package. The release notes say which mode was used.
- Private-mode rendering (D10): the committed `quotes.json` holds at most 25
  words per popover (all cited lines in a paragraph count together) plus each
  line's timestamped link. The renderer reads quotes only from this file; the PDF
  margin key needs only timestamps. Stages 1-2 are skipped on a fresh clone; CI
  starts from the committed stage-3+ artifacts and cache.
- Per mode, the CI tests are: public mode, everything; private mode, hash chain,
  cache replay, render, validation, plant exclusion and approvals. Evidence
  integrity (tampered-caption test) runs locally against the data package, and
  the README explains how an evaluator gets or regenerates that package.
- Frames are never committed. Their hashes are stored in the manifest and used
  as the cache key, so figure responses replay without the images. Diagram
  checks against the frames run only locally.

**Config schema (R1-13, R1-14).** `playlist_url`, `title`, `reader`, `languages`,
`models {writer, judge}`, `budget_usd`, `stages {code: {enabled, language},
figures: {enabled}, html: {enabled}}`, `reference_pack {repo, commit, license,
include}` (optional). A new playlist needs **no code changes**. Expected
per-playlist data: config, captions (or their hashes), the model-call cache, and
approval records.

**Code in CI (R1-15).** CPU-only PyTorch, pinned. Listings are tagged `exec` or
`display`. `exec` listings use tiny model configs, fixed seeds and no downloads;
listings that load GPT-2 weights or datasets are `display` only. Quarto `freeze`
stores executed outputs before hashing. Numeric assertions only cover
deterministic quantities (parameter counts, shapes).

**Thresholds (R1-21, R1-22).** Chunk size: 15 minutes of captions. Importance:
3 = core (must be placed), 2 = supporting, 1 = aside. Review queue: verdict
partial/unsupported, or judge confidence below a cutoff (initially 0.7). The
cutoff is calibrated on the plants the judge wrongly passed plus audit errors,
re-fitted at the day-7 checkpoint across all chapters, and reported with its
sample size. Confidence routes work; it does not prove correctness. Cache entries record the
deployment name, the model version the API reports, and the parameters; a
change in model version invalidates the entry.

**Effort and cost (R1-18, R1-20), order of magnitude, to be re-measured on the slice.**
- Capture: transcript API from a home IP, about 1 request a minute, about 45 min
  for 43 lectures. If YouTube blocks it, local Whisper on 31 h of audio takes
  roughly 3-4 h. **Full capture starts on day 1, in the background.**
- Model tokens: about 400k tokens of captions. Extraction ~125 calls; outlining
  ~10 calls; writing ~60 sections; judging ~800 paragraphs plus about 200 plants.
  Roughly 5-8M tokens per full run, i.e. tens of dollars on a mid-tier model.
  Budget ceiling: $150, enforced by `budget_usd`.
- Human time: outline approval ~1 h; review queue, if 5-10% of ~800 paragraphs
  are flagged (40-80), ~3-5 h; audit ~2 h.

**Cut line (R1-19).** *Minimum submittable book:* stages 1-6 and 9 (PDF),
citations, the planted-claim test, the evaluation report and offline replay.
Extras are dropped in this order if time runs short: figures stage → exercises →
heatmap/glossary/`why` → GitHub Pages → HTML popovers → second playlist reduced
to a smoke test → code stage reduced to display-only listings. Checkpoints: **day 3** (slice metrics), **day 8** (full PDF read; no
extras before it), **day 10** (second playlist green, or reduce it to a smoke
test with outline approval only and a DRAFT result allowed) and **day 12**
(figures only if everything else is green).

## Open Questions

1. Which models? The Azure deployment is still untested. Proposed: the judge
   uses a different model family from the writer, to avoid a model agreeing with
   itself.
2. Which second playlist? Short (3-5 videos), different field, captions available.
3. Public or private data mode? This depends on whether we may republish the
   captions; both modes are specified above.
4. Downloading audio (Whisper fallback) or video (frames): check the terms of
   service first. Without `--allow-media-download`, a lecture with no captions is
   recorded as missing, shown as a gap in the coverage inventory, and blocks
   release until it is resolved or excused in the review queue.
5. Can Quarto produce byte-identical PDFs (SOURCE_DATE_EPOCH)? Otherwise compare
   the HTML/Markdown hashes and the PDF text.
6. Is the audit threshold (at most 2 material errors in 100) right for the evaluator?

## Success Criteria

**Minimum (the submittable book; matches the cut line):**
- About 8-10 concept chapters as a PDF (Quarto + LaTeX) with a table of
  contents, code and maths, read and corrected by Mahima.
- Every factual sentence is cited and judged. The report publishes the support
  rate per chapter, plant catches *and misses* by type, and the audit error rate
  with its sample size. Targets are set after measuring, never promised.
- Every lecture appears in the coverage inventory; any unexplained missing
  lecture blocks release.
- A fresh clone plus `make book` rebuilds offline in CI (hash and cache checks).
  Checking evidence against captions is a documented local run with the private
  data package.

**Stretch (in cut-line order, each with a date and metric trigger):**
- Code stage: every `exec` listing runs in CI and every `display` listing is
  labelled; counts appear in the report.
- Second playlist through the full release gate, with no code changes (config
  plus its own data).
- HTML edition with citation popovers; GitHub Pages.
- Heatmap, glossary + index, `why`, exercises.
- Figures stage.

### R2-1 — consistency

**Problem**

> The Citation contract defines line IDs as `VIDEO@S` (whole seconds, shown as h:mm:ss, valid past 60 minutes), but pipeline stage 2 still names windows `VIDEO@mm:ss`, and stage 3 (`window_ids`), stage 6 ('against cited windows') and stage 8 ('caption windows +/-60 s') still key on those window IDs. The window ID format for lectures longer than 60 minutes (up to 94 min here) is therefore still ambiguous, and the pipeline diagram disagrees with the contract.

**Remedy**

> Give windows the same seconds-based ID scheme as lines (for example `VIDEO@S` of the window start, or `VIDEO@S-E`), and update stages 2, 3, 6 and 8 in the pipeline diagram so they use the contract's IDs and say whether the judge receives the cited lines or their enclosing windows.

### R2-2 — feasibility

**Problem**

> Writers must cite individual caption lines and the judge checks against them, but stage 2 outputs windows as 'plain text' (to remove JSON overhead) and stage 3 teaching points carry only `window_ids`. If line IDs are stripped in segmentation, the writer has no line IDs to cite and the citation-ID gate cannot validate them.

**Remedy**

> Specify a compact segment format that keeps a line ID (or second offset) on every caption line inside each window, and state that the write and verify prompts receive these line-tagged windows.

### R2-3 — completeness

**Problem**

> In private-data mode the captions may not be republished, yet the rendering contract shows readers the quoted caption lines in HTML hovers, and CI 'replays rendering from the cache'. Publishing the quoted lines in the book would republish the captions the private mode exists to withhold, and the document does not say what the reader sees in that mode.

**Remedy**

> Define the private-mode rendering: for example, popovers and margin keys show timestamps and video links only (or a short quote limit justified by the rights answer), and state which committed artifact the renderer reads in that mode.

### R2-4 — clarity

**Problem**

> The Citation contract says `validate_chapter` enforces the sentence-type rules (factual, technical, connective), but `validate_chapter` is described as the cheap, deterministic citation-ID gate. It cannot tell a factual sentence from a connective one unless something labels each sentence's type, and the contract assigns the 'no factual claim' check to the judge.

**Remedy**

> State that the writer emits a type tag per sentence, that `validate_chapter` checks only tag/citation consistency (factual needs a caption line, technical may add a ref, connective has none), and that the judge separately verifies connective sentences carry no claim.

### R2-5 — consistency
